# Security model

## Three kinds of caller

Superblink Events returns events only for repositories that the caller may read. A caller of `/github/mcp` is one of three kinds:

| Caller | Its bearer token | Who decides what it may read | GitHub token that Superblink Events keeps for it |
| --- | --- | --- | --- |
| A [browser login](browser-login.md) | A Superblink Events access token | GitHub, asked with the user's GitHub App token | The user's access token and refresh token, sealed |
| A [service](service-accounts.md) | A Superblink Events access token | The operator's grants. Superblink Events asks GitHub nothing. | None |
| A [workload](service-accounts.md#log-in-with-a-workload-identity) | A Superblink Events access token, for a token that its platform signed | The operator's grants, as for a service, since it logs in as one | None |

For a service and a workload, Superblink Events holds no GitHub token of the caller. For a browser login, Superblink Events keeps the user's GitHub App token, sealed with AES-256-GCM under `FAUCET_TOKEN_KEY`, and gives the client its own short-lived token. The client never sees the GitHub token. Whoever holds both Superblink Events' database and `FAUCET_TOKEN_KEY` can open those tokens and act as each of those users within the App's permissions, and with the App's client secret can also refresh them. That is why the App gets read-only permissions.

## Access to events

Every `/github/mcp` request carries its bearer token as `Authorization: Bearer <token>`. A bearer that starts with `fct_`, `fcr_` or `fcs_` is a Superblink Events token. Superblink Events checks it itself and never sends it to GitHub. Superblink Events mints access tokens for service clients and for the sessions of browser logins, each valid for 15 minutes on the one endpoint it was issued for, and every other Superblink Events token is 401.

Any other bearer, a GitHub token among them, is 401 too, with the same `WWW-Authenticate` challenge as a request with no token, which names the endpoint's metadata so that the client can find the login server. Superblink Events never sends a bearer to GitHub. It takes no GitHub token because GitHub cannot say what one may read: `GET /repos/{owner}/{name}` answers a fine-grained token that holds only the `Metadata` permission, or a user token of another GitHub App, for a private repository whose pull requests and checks that token cannot read, and no GitHub API reports a fine-grained token's permissions.

Because no request reaches the MCP server without a bearer token, Superblink Events turns off the go-sdk's DNS-rebinding check, which refuses a loopback listener reached under another `Host`. That check protects a local server that trusts whoever can reach it, and it refused every request on Vercel, whose runtime hands each request to Superblink Events on a loopback address under Superblink Events' public `Host`.

A browser login is checked with `GET /repos/{owner}/{name}`, sent with the GitHub token that Superblink Events keeps for the user, a user token of Superblink Events' own GitHub App. GitHub answers it for a repository where the App is installed and that the user can read, so the answer is about the user and not about a token that someone narrowed. A repository the user can't read gives the same `Forbidden` error as one that doesn't exist. Superblink Events refreshes that token first when it is about to expire. When GitHub rejects it, Superblink Events refreshes it once and asks again. Superblink Events stores each check that passes, per GitHub user and repository, and a session takes a stored check without asking GitHub only when Superblink Events made it after that session's last refresh. At each refresh Superblink Events asks GitHub again about the 50 repositories that the user used last, among those used in the last 15 minutes, and takes away those that GitHub denies. A denial takes the user's stored check of that repository away. Superblink Events keeps a denial only as a marker for 15 minutes, so that an older pass that GitHub gave after the denial cannot come back. An agent must refresh to keep calling once its 15-minute access token expires, so a browser login's `events/poll` and the start of its wait **see a revocation within 15 minutes**, plus the clock skew between Superblink Events' instances, because each instance stamps the checks and the refreshes that it makes with its own clock. A wait that started before then can run for up to 50 more seconds. A refresh never moves a session's refreshed time back, so an instance whose clock lags cannot make older checks count again. `events/subscribe` always asks GitHub.

A GitHub rate-limit answer counts as a failed check that the caller can retry, not as a denial.

**A caller of one target learns nothing from Superblink Events' answers about the events of targets it cannot read.** Every cursor, head, `hasMore`, `maxAgeMs` floor and `truncated` flag, the wait tool's cursor and event `id`, and the `cursor` of a webhook body or a gap envelope is a place among the events of the target that the call or the subscription names (see [cursors](events.md#cursors)). Other targets' events, and purges of them, change none of these values, and a cursor made by hand reads only the named target's events. Two things are not covered: how long an answer takes, because every caller's reads share one database, and [raw events](events.md#raw-events), whose `r1.` cursors still number every repository's raw events together.

**A raw event carries only what every reader of its repository may see.** Superblink Events checks only that a caller can read a repository, and anyone can read a public one. So Superblink Events drops every `release` delivery of a draft release, which GitHub shows only to people with push access, whatever its action, before it looks for an interest: no lease or subscription gets a draft that arrives after the upgrade (see [raw events](events.md#raw-events)). A draft stored before the upgrade stays until the purge clears raw bodies.

One login can hold 10 waits open at once per process, and run 5 `events/poll` calls at once, typed or raw names together. The call over either limit fails at once, and a poll over it gets `ResourceExhausted` with `data.limit` `polls`. Embedders can change them with `Deps.MaxWaitsPerLogin` and `Deps.MaxPollsPerLogin`. These limits hold per process, so the production deployment also limits each IP address at the edge (see the [firewall](deploy.md#firewall)).

## Principals and scopes

A host that embeds Superblink Events tells it who calls. Its `PrincipalFrom` returns a `Principal` from `NewOAuthUser` (a user of a browser login), `NewService` (a service) or `NewPrincipal` (a GitHub user whose GitHub token `TokenAuthorizer` asks GitHub with, which holds every scope). The wait tool and `events/poll` need `events:read`, `events/subscribe` and `events/unsubscribe` need `events:subscribe`, and `events/list` needs none. A `Principal` built by hand, or one whose `Login` changed after a constructor built it, is no kind of caller: every method but `events/list` answers it `authentication required`.

An `Authorizer` answers `RepoID`, which may remember, and `RepoIDFresh`, which every renewal calls and which must ask again. One that sends each kind of principal to another `Authorizer` passes both calls on. `TokenAuthorizer` answers a caller without a GitHub token with `ErrNoAccess` and asks GitHub nothing. A host that builds a principal from a GitHub token that a caller sent takes on the weakness above: GitHub answers `GET /repos/{owner}/{name}` for a token that cannot read the repository's events. Superblink Events' browser login builds one only from the token of Superblink Events' own GitHub App.

The `Authorizer` decides a `repo` [target](events.md#targets). An `owner` or `all` target is for a service only: Superblink Events refuses it to every other principal with `ErrNoAccess` and asks nobody. For a service it asks `Deps.ServiceGrants`, which `oauth.ServiceAccess` implements from the client's grants, and without it Superblink Events refuses those targets to a service too. Like an `Authorizer`, it has a fresh form of each call, which every renewal calls and which reads the client again. An `org:` grant covers every repository of the account that held its login when the grant was set, also one made after the grant and under any later login, and `all` every repository that Superblink Events receives deliveries from, private ones included (see [service-accounts.md](service-accounts.md#grants)).

## Repository names

A service's `repo:` grant names a repository, and Superblink Events finds its ID by the name that signed deliveries gave it under the login that its owner holds (see [service-accounts.md](service-accounts.md#grants)). A rename or a transfer can give the old name, or the old login, to another repository or account, so a name that Superblink Events failed to move, or moved back, would let the grant read a repository that it does not name.

GitHub signs the body of a delivery and no header, and the body holds no time that orders deliveries, so Superblink Events cannot tell a delivery that GitHub just sent from one that someone kept, nor order two deliveries. GitHub shows each delivery's body and signature to whoever can read the hook's recent deliveries, for 3 days, so a hook admin can keep one and send it again under any delivery GUID. So a delivery adds what Superblink Events lacks, but before it changes a name that Superblink Events holds, Superblink Events asks GitHub, which alone knows the current names, at `FAUCET_GITHUB_API_URL` and with no token:

- **Logins.** A delivery that names an account under the login that Superblink Events holds for it changes nothing, and one that names an account that Superblink Events has not seen, under a login that no account holds or held, adds it. Any other delivery means that GitHub renamed the account, gave its login to another account, or that the body is old, and Superblink Events cannot tell which. Then Superblink Events asks `GET /user/{id}` and writes the login that GitHub gives, whatever the delivery says. When GitHub does not answer (404, its rate limit, an error, or no answer within the 4 seconds that the lookups of one delivery get), Superblink Events fails closed: it quarantines the account and the account that holds the delivered login, and neither holds a login until GitHub gives one. A quarantined account heals on its own: every delivery that names it, under any login, asks GitHub again, and the answer gives the account its login. Superblink Events asks about one account at most once a minute, and a delivery within that minute that would change a login gets no answer, so it quarantines too; the next delivery after the minute heals it. Superblink Events asks for one account, and for one repository, under a lock in the database, so two answers are written in the order in which Superblink Events asked, and a delivery that waited for another's answer about the same account and finds the login that it names asks nothing. One process runs at most 4 lookups at once, each holding one database connection, and only for a delivery that would change a name. A delivery's lookups, waits for a free lookup and for the lock included, end 4 seconds after the first wait starts; one that gets no lookup or no lock in time asks nothing.

  **The cost of failing closed:** while an account is quarantined, every grant that names its repositories by name refuses: a `repo:` grant of any of its repositories, the `owner` target of an `org:` grant, and the repositories that an `org:` grant reads by name. A hook admin's replay of an old delivery while GitHub cannot answer (an outage, or the 60 requests of the hour spent) therefore pauses those reads for the account until GitHub answers and a delivery of the account arrives. No grant reads a repository under a name that GitHub no longer gives it. An operator who cannot wait looks up the account's current login on GitHub and writes it: `UPDATE faucet_owners SET login = '<login>', quarantined_at = NULL WHERE owner_id = <account ID>`, after making sure that no other row holds that login unquarantined.
- **Repositories.** Only a Repositories delivery that renamed or transferred the repository changes its names. Superblink Events judges each such body once, recording its SHA-256 in the transaction that writes the names, and answers 500 to one that it could not write, so that [redelivery](redelivery.md) asks for it again. For a body that it has not judged, Superblink Events asks `GET /repositories/{id}`. GitHub answers for a public repository, and Superblink Events writes the owner and name that GitHub gives, not the body's, and lifts a quarantine. An answer that gives the name that the body moved the repository from, and not the body's new name, can be GitHub lagging behind the rename or a kept body of a rename that GitHub undid since. Superblink Events cannot tell which, so it quarantines the repository and keeps the body as judged, so that the body, sent again under any delivery GUID, asks GitHub nothing and binds nothing. Only a later rename or transfer that GitHub answers, or the operator, lifts that quarantine. GitHub answers 404 for a private repository to a client with no token, and may not answer at all. Then Superblink Events judges the body by the name that it holds. A fresh one from that name takes its names. A fresh one from any other name may follow a rename that Superblink Events missed or be an old body sent again, and Superblink Events cannot tell which, so it binds neither name and quarantines the repository: it answers to no name, under a `repo:` grant or an `org:` grant. No delivery lifts a quarantine: a missed rename can come later from the name that Superblink Events holds, and kept bodies can chain, so Superblink Events keeps no name of the rename that caused it either. One that redelivery asked for takes its names only from the name that Superblink Events holds. A quarantine lasts until GitHub names the repository on a later rename or transfer, or until an operator looks up the repository's current owner and name on GitHub and writes them to its row: `UPDATE faucet_repos SET owner_id = <owner ID>, owner_login = '<owner>', full_name = '<owner>/<name>', quarantined_at = NULL WHERE repo_id = <ID>`. Deleting the row instead would let the next delivery, which can be a kept body, give it any name.

What Superblink Events still cannot tell apart:

- **A private repository, or a public one while GitHub does not answer: a signed rename or transfer that Superblink Events never judged, from the name that Superblink Events holds, takes its names.** Such a body is one that never reached Superblink Events, one that Superblink Events took before migration `000019_repo_renames`, or one that it answered 500 to. Its names stay until the next rename or transfer, when Superblink Events moves the repository from the name that it holds. A body from any other name only quarantines the repository, which denies its grants and gives none. Superblink Events logs `a rename or transfer of the repository never reached faucet` whenever that happens. Giving the hook a new secret makes every kept body useless.
- **Two renames of such a repository that arrive out of order.** Superblink Events does not count on GitHub to send deliveries in order. When the older of two renames arrives last, and redelivery did not ask for it, it binds its names until the next rename or transfer.
- **GitHub's rate limit.** GitHub gives a client with no token 60 requests an hour for each IP address, shared with whatever else calls it from that address. Superblink Events asks about one account at most once a minute and about each rename body once, but someone who holds many kept bodies can spend the hour's requests. Then accounts whose deliveries change a login are quarantined, and renames are judged by the names that Superblink Events holds, as above. GitHub answers 404 without a token for an [Enterprise Managed User](https://docs.github.com/en/rest/users/users#get-a-user-using-their-id), or a GitHub App bot in an organization that uses them, so such an account stays quarantined after a rename until an operator writes its login, and a GitHub Enterprise Server that answers no request without a token does the same to every renamed account.

## The browser login

These checks keep another site, another browser and another client from finishing a user's login:

- **Another site cannot press Continue.** The consent page sets a cookie for its own login, and its form carries a token derived from that cookie. Superblink Events goes on only when the post carries the cookie, the matching form token and an `Origin` that equals `FAUCET_PUBLIC_URL`. Any other post is refused and stores nothing, so a page of another site that posts the form makes nothing. Continue works only once the page has been visible and in focus for 500 milliseconds, so that a page of another site cannot open the consent page under a click that the user meant for that site, such as the second click of a double-click. A press that began before then does not count.
- **Each login has its own cookies.** Their names end with the login's ID, so two logins in one browser do not mix. They are `__Host-` cookies, which only Superblink Events' own origin can set, over `https`.
- **GitHub's answer counts only in the browser that pressed Continue.** The state that Superblink Events sends to GitHub, and the PKCE verifier of Superblink Events' own exchange with GitHub, both derive from a random value in a second cookie. A callback in another browser is refused.
- **Superblink Events redirects to a client only at the end.** `/oauth/authorize` answers every error with a page and never with a redirect, because nothing proves yet that the browser is the user's. Only the callback redirects to a client, and the redirect names Superblink Events in `iss` (RFC 9207).
- **A code works once, for 60 seconds.** A code that comes back after its redemption ends the session that it made.
- **PKCE runs both ways.** A client must send an S256 challenge and redeem its code with the verifier. Superblink Events uses PKCE with GitHub too.
- **A login after a revocation at GitHub serves no session of before.** Every login of one GitHub user stores its GitHub tokens in the one pair that all the user's sessions share. Before a login replaces that pair, Superblink Events asks GitHub whether it still takes the stored pair, and holds the user's row meanwhile. When GitHub rejects it, or does not answer, the same transaction that stores the new pair ends every session of the user and every code of the user that no client redeemed yet. So a client that kept a Superblink Events server refresh token, or a code, while the user revoked Superblink Events' App at GitHub cannot use the tokens of the user's next login, made through any client. Each check asks GitHub once: `GET /user` while the stored access token lasts, or a refresh after that, whose new pair Superblink Events drops.
- **Refresh tokens rotate.** Each refresh gives a new refresh token. A refresh token that comes back 30 seconds or more after its first use ends its session, because the token then has two holders. Within those 30 seconds it trades again, because the parallel requests of one agent send one token at once. Of the tokens that such requests get, the next refresh retires the ones that the agent did not keep, and one of those that comes ends the session too. Superblink Events keeps the hash of every refresh token of a session until the session goes, so a stolen token ends the session however late its holder sends it.
- **Client documents come through the guarded client** of [callback URLs](#callback-urls): `https` and public addresses only, and no redirects. Superblink Events builds that client itself, so a host that embeds Superblink Events cannot give it another. A fetch must end within 3 seconds, and the document must be 5 KiB at most. A document that holds a client secret is refused, because anyone can read it.
- **The consent page shows the host, not the name.** The host of the client ID is the large text, and the name that the document gives is marked as unchecked, because anyone can write any name in a document. The host must be ASCII, with an internationalized name in its `xn--` form, and the name may hold no control or format character, so that neither can pass for another.
- **Redirect URIs match exactly.** A request's redirect URI must equal one of the document's byte for byte, and a loopback `http` one may differ in its port only (RFC 8252). The token request must name the same redirect URI. Schemes that a browser runs, such as `javascript`, are refused.
- **The pages load nothing and run one script,** the wait of Continue, which their Content-Security-Policy allows by its hash. No other site can frame them.

Anyone who serves a valid document can open `/oauth/authorize`, so Superblink Events bounds what that costs. It keeps up to 64 documents, each for as long as its cache headers let a shared cache keep it and 5 minutes at most, and fetches no client ID on its own host. The consent page stores nothing: its form carries the request, sealed with AES-256-GCM for the cookie of the browser that got the page, under a key that HKDF-SHA256 derives from `FAUCET_TOKEN_KEY` for consent forms alone, and Superblink Events stores the request only when that browser presses Continue. So no number of requests uses up anything that another user's login needs. A script can still store rows, one for each GET and POST pair, because it can keep the cookie and send Superblink Events' `Origin` itself. Put a per-IP rate limit on `POST /oauth/authorize` at the edge, such as the Vercel Firewall rule in [deploy.md](deploy.md#firewall); `/cron/purge` deletes such a row once it expires, 10 minutes after the GET. Superblink Events keeps the failure of a fetch for 1 minute, so a client ID whose fetch failed costs one fetch a minute however often it comes, and logins that start at once share one fetch. A client ID with a new path, or a document sent with `no-store`, still costs one fetch per request. Superblink Events sets no limit per host, because bad client IDs on a host could use it up and lock out that host's real client.

## Workload identities

A workload logs in as a service client with a token that its platform signed, so Superblink Events trusts the platform's issuer to say which workload holds the token. A trust rule names that issuer and pins claims that only the one workload's tokens hold. Superblink Events takes a token whose signature verifies with the issuer's key, whose `aud` is Superblink Events' public URL alone, so that a token that the platform made for another service does not log in, and that has not expired. It then mints its own token, which lasts 15 minutes and never past the platform's token. Superblink Events remembers no platform token, so a copy of one logs in as the client, again and again, until its `exp`. Superblink Events takes no token that lives more than 24 hours, from its `iat` or `nbf` to its `exp`. Vercel documents 2 hours for the token of a production function. A mounted Kubernetes token lasts its `expirationSeconds`, and one that `kubectl create token` made lasts its `--duration`. Superblink Events asks the cluster nothing (no TokenReview), so such a token logs in after its pod or its service account is gone, until it expires or the operator runs `faucet clients untrust` or `disable`.

- **An issuer that serves many tenants is pinned to one tenant by ID.** Vercel signs the tokens of every team with the same keys. Superblink Events requires a Vercel rule to pin the team's and the project's IDs, never only a name that a team can rename and another can take, and it never trusts `https://oidc.vercel.com`, the issuer that every Vercel team shares (see the [Vercel warning](service-accounts.md#example-a-vercel-function)). It refuses the issuers of GitHub Actions, on github.com and on GHE.com (`token.actions.<subdomain>.ghe.com`), and gitlab.com until a test logs in with their tokens. GitHub Enterprise Server and self-managed GitLab fall under the rule for any other issuer, which requires only `sub`, and are not a supported target. A rule for any other issuer must pin `sub`.
- **A platform's token logs in only through the token exchange** (RFC 8693), never as a client assertion (RFC 7523): no grant of Superblink Events' takes one. The platform's token proves which workload calls, and the operator's trust rule, not the token, says which client it may act as.
- **Keys come through the guarded client** of [callback URLs](#callback-urls), which Superblink Events builds itself: `https` and public addresses only, and no redirects. The discovery document and the key set that it names must arrive within 5 seconds together, and each must be 32 KiB at most. Superblink Events fetches only the issuers that an operator trusted, for a token that names one, so a request cannot make Superblink Events fetch from anywhere else. Pasted keys are never fetched.
- **Superblink Events keeps an issuer's keys for 5 minutes**, so a key that the issuer drops stops working within 5 minutes. It fetches sooner only for a token whose `kid` the keys lack, and at most once a minute per issuer, so tokens with made-up `kid`s cost one fetch a minute. Within that minute such a token gets the 400 `invalid_client` of a token that no rule verifies, so that a made-up `kid` tells a caller nothing about the client. A key that the issuer adds works from the next fetch. It keeps the keys of up to 64 issuers.
- **A failed fetch keeps the keys that Superblink Events holds** until their 5 minutes end. Superblink Events keeps the failure for a minute, so while an issuer fails after its keys ran out, Superblink Events answers each login of that issuer 503 `temporarily_unavailable` with `Retry-After` set to the seconds left of the minute, and fetches again at the first login a minute after the failure. The answer names no cause, and the log has it. It does tell a caller with any token that names the issuer that the client trusts the issuer and that its keys fail.

## Callback URLs

In webhook mode Superblink Events makes outbound requests to URLs that clients choose, so it guards them against SSRF:

- **`allowlist` mode** (the default) only sends to origins that the operator listed.
- **Every outbound request**, including handshakes, goes through a guarded client (`faucet.NewHTTPClient`). It speaks `https` only and resolves the host. It refuses the request if any resolved address is not public (loopback, private, link-local, CGNAT, multicast, NAT64 and similar ranges), then dials the address it checked, so DNS can't change between the check and the connection. It follows no redirects, ignores proxy variables, and times out after 5 seconds. It refuses a response that declares a body over 64 KiB or that has headers over 16 KiB, and a delivery attempt that gets one counts as `http_5xx` and is retried. A delivery closes the body unread. A handshake reads its answer, and fails one that is longer than a challenge answer needs.
- A host that resolves to an internal address fails as `connection_refused`, the same as a closed port, so a caller can't map your network.

In `handshake` mode, any public endpoint that answers the challenge can receive events. Use `allowlist` when a public endpoint could front an internal service.

A binary built with `-tags faucet_e2e` lets the guarded client reach loopback over `http`, for the end-to-end tests. No environment variable does this, and the tagged binary logs a warning at start. **Never ship it.**

## Secrets

- **Subscriber secrets** are sealed with AES-256-GCM under `FAUCET_WEBHOOK_KEY`, and never returned or logged.
- **The GitHub tokens of browser logins** are sealed with AES-256-GCM under `FAUCET_TOKEN_KEY`, and never returned or logged. Once no session and no login request names a user's pair, `/cron/purge` deletes it a day after its last update. A sealed token names its user and its field in the data that the seal covers, so a token copied to another row or field does not open. Superblink Events sends the access token only to `FAUCET_GITHUB_API_URL`, and the refresh token only to GitHub's token endpoint at `FAUCET_GITHUB_URL`, and follows no redirect. A token that does not open fails its user's checks and ends no session (see [rotating the key](browser-login.md#rotate-the-token-key)).
- **`FAUCET_GITHUB_APP_CLIENT_SECRET`** goes only to GitHub's token endpoint, with a user's code or refresh token. Keep it in production only.
- **`CRON_SECRET`** guards the `/cron/*` routes. With it unset, they answer 503 and run nothing.
- **Client secrets** of service clients are shown once, when an operator makes the client, and kept only as SHA-256 hashes.
- **Superblink Events' own tokens** are kept only as SHA-256 hashes too: access tokens, refresh tokens, codes, and the cookie values and GitHub state of a login in progress. `/cron/purge` deletes each access token once it expires, and each session with its refresh tokens once the session ended or went unused for 180 days. A client revokes a token of its own at `POST /oauth/revoke` (RFC 7009): a refresh token ends its session.
- **`FAUCET_HOOK_TOKEN`** is the only GitHub token that Superblink Events holds for itself. GitHub offers no grant narrower than one that can also edit or delete the hook, so give it to a machine user and keep it in production only. Superblink Events uses it for exactly two endpoints: listing a hook's deliveries and asking for a redelivery.
- Startup errors name a bad variable but never its value.
